# AI Model Loading: Development vs Production

A small FastAPI project demonstrating why an ML model should usually be loaded once when an application starts, rather than loaded from disk for every prediction request.

## What this project demonstrates

- `wrong_main.py` loads `model.pkl` inside the prediction endpoint, so each request repeats the model-loading step.
- `main.py` loads the model during application startup and reuses it for prediction requests.
- Reusing the loaded model avoids repeated deserialization and disk I/O, which can reduce request latency and wasted compute work.

> This example reduces repeated model-loading work. It does not reduce the number of HTTP API calls, and it does not eliminate the cost of running a prediction. Actual savings depend on the model, traffic, and deployment setup.

## Run locally

These commands are for Ubuntu/Linux and should be run from the project directory.

### 1. Create and activate a virtual environment

```bash
python3 -m venv venv
source venv/bin/activate
```

### 2. Install dependencies

If your file is currently named `reuirements.txt`, correct the spelling first:

```bash
mv reuirements.txt requirements.txt
```

Then install the packages:

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Your dependencies should include the packages used by the project, such as `fastapi`, `uvicorn`, `scikit-learn`, and `joblib`.

### 3. Train and save the model

```bash
python train_model.py
```

This creates or updates `model.pkl`.

### 4. Start the API

```bash
uvicorn main:app --reload
```

To compare the version that reloads the model on every request, stop the first server and run:

```bash
uvicorn wrong_main:app --reload --port 8001
```

### 5. Test the API

Open the interactive API documentation:

- Main implementation: http://127.0.0.1:8000/docs
- Comparison implementation (if running): http://127.0.0.1:8001/docs

Send a `POST` request to `/predict` with a JSON body such as:

```json
{
  "text": "I love this product"
}
```

The API returns the input text and the predicted class.

## What changes between the two versions?

| Implementation | When the model is loaded | Effect |
|---|---|---|
| `wrong_main.py` | During every prediction request | Repeats disk loading and deserialization work |
| `main.py` | Once per application worker at startup | Reuses the in-memory model for subsequent requests |

Loading once per worker is not the same as loading once for an entire multi-worker deployment. Each worker process may have its own model instance, which affects memory usage.

## Production considerations

**Benefits**
- Avoids repeated model deserialization on each request.
- Can lower request latency and reduce unnecessary CPU and disk work.
- Gives the application a clear startup point for loading the model.

**Trade-offs and limitations**
- The model occupies memory while the worker is running.
- Multiple worker processes may each load their own model, increasing RAM usage.
- Startup can take longer while a large model is loaded.
- Model updates need a deliberate reload/restart strategy.
- Loading a model once does not reduce HTTP request count or the compute cost of each prediction.
- This is a learning example, not a complete production deployment. Real systems should measure latency, throughput, memory, errors, and model quality.

Only load pickle/joblib model files from trusted sources: deserializing untrusted files can execute malicious code.

## Key takeaway

In production, avoid repeating expensive work unnecessarily. Measure where time and resources are being spent, then reuse resources safely when appropriate.
